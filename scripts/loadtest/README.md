# 实时协作容量压测（Socket.IO / 单板）

本目录给出「这块白板最多能支持多少人同时协作」的量化口径、可复现压测脚本和一次实测结论。

- 脚本：[realtime-load.mjs](./realtime-load.mjs)
- 写路径优化**前**基线：[results/realtime-20261117-143255.md](./results/realtime-20261117-143255.md)
- 写路径优化**后**：[results/realtime-20261117-154436.md](./results/realtime-20261117-154436.md)
  （同目录 `.json` 含完整分布、Redis 分命令速率、PG 连接等明细）

> 结论先行：本机 dev server（单实例、单板、每端 4Hz 光标 + 1Hz 元素更新）在 **20 人**以内是舒适区；
> **50 人**开始元素更新排队、**100 人**时 Node 单核被打满（92–99%，光标 p95 8–9s、投递率 40–48%）。
>
> 写路径批量提交后，**元素写入不再是 50 档的瓶颈**（PG 事务率 106 → ~14/s、池 9/10 → 0/10、
> Redis `eval` 150 → 56/s），20 档 ack p95 从 136ms 降到 38–49ms；但**拐点仍在 50**，
> 因为剩下的瓶颈是单核上的光标扇出，留给下一项优化。详见 §5.1。

## 1. 怎么量化：指标与拐点判定

并发容量不是白板的一个固定属性，而是「给定事件频率、事件大小、可接受延迟」后的一个点。因此分四条链路测：

| 类别 | 指标 | 采集方式 |
| --- | --- | --- |
| 接入 | 成功 join 数、join p50/p95、连接错误、掉线数 | 每个 socket `connect → joined` 计时，失败按错误码归类 |
| 交互延迟 | 光标广播 p50/p95、op ack p50/p95、op 广播 p50/p95 | 见下方「延迟口径」 |
| 吞吐 | 投递事件/s、投递/期望、op 提交/s、op 拒绝率 | 接收端计数 ÷ 测量时长；期望值 = `N(N-1)·光标Hz + N²·opHz` |
| 资源 | 服务端进程 CPU/RSS、Redis 命令/s 与内存、PG 活跃连接/池上限/事务速率、压测端 event loop p95 | 常驻采样器 0.5s 一次，见脚本 |

延迟口径（都含真实服务端处理 + 广播，不是纯 RTT）：

- **join**：`connect` → 收到 `joined`（身份解析、权限查询、presence 登记、加入 room）。
- **光标**：发送端 `emit` 时刻与接收端到达时刻配对。服务端合帧后仍要能精确计量，脚本在 `cursor:move`
  里带一个可选的 `t`（`performance.now()`），服务端原样回带；所有压测端在同一进程，时钟同一。服务端不认
  这个字段也不影响运行（会退回按连接有序投递配对），生产客户端则不发它。
- **op ack**：`op:submit` → 对应 opId 的 `op:ack`。
- **op 广播**：发送端把毫秒时间戳编进 opId 首段，接收端解析 `op:apply` 的 opId 后与本地时钟相减。

拐点判定（阈值写死在脚本 `THRESHOLDS`，可按产品口径调整）：

- **PASS**：join 全成功；join p95 ≤ 300ms；光标 p95 ≤ 150ms；ack p95 ≤ 200ms；广播 p95 ≤ 250ms；
  失败率 ≤ 1%；服务端进程 CPU ≤ 85%（单核口径）；投递率 ≥ 90%。
- **DEGRADED**：有指标越线但未到硬失败。
- **FAIL**：join 成功率 < 90%，或失败率 > 5%，或投递率 < 75%，或 ack/光标 p95 超过阈值 2.5 倍。
- **拐点** = 第一个非 PASS 的档位；另报「吞吐饱和」（供给增长 ≥1.5 倍而投递 <1.25 倍，或投递率 <90%）。

为什么分两条路径：光标是高频、不落库的广播（服务端合帧后每个房间固定 30 条/s，但每帧仍要写到房间内
每个 socket，接收侧成本仍随人数线性增长）；元素更新是低频、但每批要过一次数据库事务。
两者的上限成因不同（前者单核写扇出、后者单板串行写），拐点通常不在同一档。

## 2. 运行方式

前置：dev server 已启动（`npm run dev` 或 `npm run dev:server`），Redis / Postgres 可用，`.env` 已有
`DATABASE_URL` / `REDIS_URL`。脚本只做客户端，**不启动、不重启、不 kill 任何服务进程**。

```powershell
# PowerShell（默认 5/10/20/50/100，每档预热 2s + 测量 10s）
node scripts/loadtest/realtime-load.mjs

# 指定被测进程，CPU/RSS 才能采到（Windows 下自动探测也可，偶尔会因 Get-NetTCPConnection 慢而失败）
node scripts/loadtest/realtime-load.mjs --server-pid <pid>

# 自定义负载
node scripts/loadtest/realtime-load.mjs --levels 10,30,60 --duration 15 --cursor-hz 6 --op-hz 2 --op-bytes 1024
```

```bash
# bash
node scripts/loadtest/realtime-load.mjs --levels 5,10,20,50,100
```

主要参数：`--base`（默认 `http://127.0.0.1:${PORT:-8080}`）、`--levels`、`--duration`、`--warmup`、
`--cursor-hz`、`--op-hz`、`--op-bytes`、`--observers`、`--join-timeout`、`--out`、`--server-pid`、
`--keep`（保留测试账号，默认清理）。`--cursor-hz 0` / `--op-hz 0` 表示只发另一类流量，用来归因；
`node scripts/loadtest/realtime-load.mjs --help` 查看全部。

脚本行为与安全边界：

1. 注册一次性账号 → 建一块测试板 → 签一张 **edit** 分享链接；每个压测 socket 用该链接以匿名身份加入，
   因此 presence 里是 N 个独立连接，而不是 1 个用户开 N 个标签页。
2. 每档先全部 join，再预热（预热结束清零延迟/计数），然后测量；档位之间断开并冷却 1.2s。
3. 延迟样本只在前 `--observers` 个接收端入直方图，其余端只计数，避免压测进程自己成为瓶颈；同时采样
   压测端 event loop 延迟用于自检。
4. 逐档输出并写 `results/realtime-<时间戳>.{json,md}`，控制台打印结论表与拐点。
5. 结束/`Ctrl+C` 时：断开全部 socket、删除测试账号（级联删除测试板）、清理该板的 `seq:`、`idem:*`、
   `dirty:boards` 残留，并终止 CPU 采样 helper 进程。被测服务完全不动。

| 客户端渲染 | 前端只渲染前 40 个远端光标（`MAX_CURSORS`） | 只影响显示，不影响服务端容量 |

## 4. 理论天花板由哪一条决定

1. **元素写入（先撞的天花板）**：同一块板的写事务被 `pg_advisory_xact_lock` 全局串行，单板吞吐 ≈ `1 / t_txn`。
   本次实测在 50 op/s 时 PG 事务率 ≈ 106 次/s（每 op 两次事务口径：`last_seq` 查询 + 写事务），
   ack p50 已到 554ms、池占用 9/10 —— 即 dev 环境下 **单板约 50 op/s 封顶**（t_txn ≈ 10-20ms，
   含 Windows + tsx + debug 日志的开销）。加到 100 op/s 后写路径不是「变慢」而是被光标路径饿死
   （事务率掉到 7.4/s、`eval` 掉到 1.5/s）。§5.1 的攒批优化把事务率降到 ~14/s、池占用降到 0/10，
   写路径不再是 50 档的瓶颈，但「单板串行」这一结构没变，50 op/s 仍是该档的实际上限。
2. **广播写扇出**：一条消息只序列化一次，但服务端仍要为房间内 N 个 socket 各写一帧（ws 帧 + 客户端解析），
   成本 O(N × 消息数/s)。合帧后光标消息数与人数解耦（每房间固定 30 条/s；§5.4 起小房间自适应到
   40–70 条/s，但人数少、扇出小），所以单独压 100 个 4Hz 光标只花 21% CPU、p95 61ms（§5.2）；
   真正压满单核的是「光标帧 + `op:apply` 全房广播」叠加：
   100 档 = 100 op/s × 100 个接收者 = 1 万帧/s，把 ack p50 抬到 ~330ms，CPU 51–65%。
   这一条是 §5.2 之后的新天花板，下一步应从「减少接收者 / 减少每帧字节」入手。
3. **presence / 成员数 / socket.io 配置 / 限流都不是决定项**——前两者没有上限，后两者阈值远高于实测拐点。
   但 presence 的「每次 join 广播全量名单」会把 join 风暴放大成 O(N²) 字节：100 人同时进房时 join p95
   已经是 1.48s，这部分会先体现在接入上，而不是稳态延迟上。

所以本机单实例的容量天花板是 **「Node 单核（广播写扇出）+ 单板 advisory lock（元素写入）」的较小者**，
而不是某个可调常数。§5.1 后写路径不再是短板；§5.2 后光标也不再是短板；§5.3 后 join 突发被压掉，
当前只剩 `op:apply` 的全房广播写放大（见 §8 待办）。

## 5. 实测结论表

环境：Windows、20 核 / 31.6GB、单实例 dev server（tsx watch、debug 日志）、Redis + 本地 Postgres；
负载：每端光标 4Hz + op 1Hz（op data ≈ 256B）；每档预热 2s + 测量 10s。

| 并发 | 加入成功 | join p95 (ms) | 光标 p95 (ms) | op ack p95 (ms) | op 广播 p95 (ms) | 投递事件/s | 投递/期望 | 失败率 | 掉线 | 服务端 CPU | RSS (MB) | Redis 命令/s | PG 活跃连接 | 判定 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 5 | 5/5 | 11.97 | 4 | 30.66 | 31 | 103 | 98% | 0.0% | 0 | 4.2% | 93.8 | 79.7 | 0/10 | PASS |
| 10 | 10/10 | 14.11 | 4 | 27.57 | 28 | 446.4 | 97% | 0.0% | 0 | 5.9% | 97.3 | 153.7 | 0/10 | PASS |
| 20 | 20/20 | 43.96 | 15 | 136.32 | 139 | 1873.5 | 98% | 0.0% | 0 | 14.7% | 100.4 | 302.6 | 1/10 | PASS |
| 50 | 50/50 | 284.37 | 92 | 1056.84 | 1062 | 12300.2 | 100% | 0.0% | 0 | 76.5% | 110.6 | 755.2 | 9/10 | FAIL |
| 100 | 100/100 | 1482.22 | 9058 | — | — | 19555.5 | 39% | 17.4% | 0 | 98.8% | 133.3 | 207.1 | 0/10 | FAIL |

读法：

- **20 人**：光标 15ms、元素 ack 136ms，CPU 15%，全部达标。
- **50 人**：接入和光标广播还能过（join p95 284ms、光标 92ms），但元素更新 ack p95 1.06s、池 9/10，
  已经不可用——这是**功能拐点**。Redis 速率 755/s 里约 `eval 150/s`（3 次/op）、`publish 250/s`、
  `get/incr/zadd 50/s` 各对应一次 op 级命令。
- **100 人**：join p95 1.48s；光标 p95 9.06s、只投递 39% 期望量；元素提交 19.1% 直接 `INTERNAL`
  （池获取超时），1000 次提交在测量窗口内 0 ack，PG 事务率从 106/s 掉到 7.4/s —— **接入也崩**。
- 三次重复运行结论一致：拐点都在 50；50 档 ack p95 在 0.9–2.6s、光标 p95 在 84–172ms 之间浮动；
  100 档每次都是光标秒级 + 元素路径近乎全挂。数字会受 dev 日志级别、Windows 后台任务、以及
  **压测期间恰好有其他进程修改 `apps/server/src` 导致 tsx 重启**影响（本次已剔除这种样本）。
- 负载口径偏保守也偏乐观：1 op/s/端 远低于真实拖动时 Excalidraw 的变更频率（客户端没有固定节流，
  拖动期间会持续产生 op），所以「50 op/s 封顶」对应到真实拖动场景，可支撑人数会更低；
  反之光标 4Hz 也低于部分前端的 16Hz 光标节流上限。调 `--cursor-hz` / `--op-hz` 可覆盖这两个方向。

## 5.1 写路径批量提交后的复测（2026-11-17）

改动（只动写路径，`apps/server/src/realtime/{board,opStore,seq,opBatcher}.ts`）：

- **同板攒批**：每个 board 一条 FIFO 队列、单飞执行，短窗口内的 op 合并进一个事务；
  入队顺序 = seq 分配顺序 = 落库顺序（比原来多 socket 并发 handler 更严格）。
- **去掉每批 `select last_seq`**：改为 Redis `INCRBY` 取号段；只有 `seq:` 键缺失（首次 / Redis 重建）
  才回源 `boards.last_seq` 播种，语义与原来逐 op 播种一致。
- **Redis 往返**：`claim` / 取号段 / `done` 三段都改为 pipeline，每批各 1 次往返（原来是每 op 3 次）。
- **锁粒度没有细化**：每个写事务都要 `update boards set last_seq = greatest(...)`，同一行的行锁仍会把
  单板写串行化；改成按元素加 advisory lock 不会提高单板吞吐，只会扩大死锁面。批量提交已经把
  事务数降了 6–7 倍，所以这一条按「视情况」判定为不改。

复测（同一台机器、同样的 2s 预热 + 10s 测量、同样的 4Hz 光标 + 1Hz op；括号内是 3 次复测的范围）：

| 并发 | 光标 p95 前 → 后 | op ack p95 前 → 后 | 投递率 前 → 后 | CPU 前 → 后 | PG 活跃 前 → 后 | 判定 前 → 后 |
| ---: | --- | --- | --- | --- | --- | --- |
| 5 | 4 → 5ms | 30.66 → 20.32ms | 98% → 98% | 4.2% → 4.9% | 0 → 1/10 | PASS → PASS |
| 10 | 4 → 5ms | 27.57 → 29.47ms | 97% → 97% | 5.9% → 9.1% | 0 → 0/10 | PASS → PASS |
| 20 | 15 → 18ms | **136.32 → 38.23ms**（38–49） | 98% → 97% | 14.7% → 15.4% | 1 → 0/10 | PASS → PASS |
| 50 | 92 → 202ms（157–202） | **1056.84 → 1021.5ms**（487–1021） | 100% → 100% | 76.5% → 68.5% | **9/10 → 0/10** | FAIL → FAIL（一次 DEGRADED） |
| 100 | 9058 → 8083ms | — → — | 39% → 45% | 98.8% → 92.4% | 0 → 0/10 | FAIL → FAIL |

写路径内部成本（50 档）：

| 指标 | 前 | 后 |
| --- | ---: | ---: |
| PG 事务/秒（`xact_commit`） | 106.2 | 13.6–15.0 |
| Redis `eval`/秒 | 150.2 | 56.3–57.6 |
| PG 应用活跃连接峰值 | 9/10 | 0–1/10 |
| 每 op 的 DB 事务数 | 2（`last_seq` 查询 + 写事务） | ≈0.3（一批一个事务，均值约 3.5 op/批） |

怎么读：

- **20 档明显变好**：ack p95 从 136ms 降到 38–49ms，p50 从 26ms 降到 19ms；说明原来的「每 op 两次
  事务口径 + 3 次 Redis 往返」在 20 人时就已经开始排队。
- **50 档的写路径被修好了，但档位没有翻绿**：池占用从 9/10 降到 0/10、事务率降 6–7 倍，说明元素
  写入本身已不再是瓶颈；剩下的 ack 延迟（p50 250–415ms）来自单核被光标扇出占住后的事件循环排队，
  光标 p95 也从 92ms 浮到 157–202ms。这正是下一项「光标扇出」要处理的部分。
- **拐点没有移动，仍在 50**；变化的是失败原因：从「写路径把 DB 池打满、ack 秒级」变成「单核光标
  路径接近饱和、50 档在阈值边缘」，100 档依旧是单核打满导致光标秒级 + 投递不足。
- 50 档数字的离散度较大（ack p95 487–1021ms），与基线本身 0.9–2.6s 的波动同量级；比较时应看
  事务率 / 池占用 / Redis 往返这些**结构性问题**是否消失，而不是单次 p95。

语义校验（临时脚本，跑完已删除）：6 个 socket 各一次提交 10 条 op → seq 唯一且连续覆盖 1..60、
每端 seq 严格递增；重复提交整批 → 全部 `duplicate=true` 且 seq 不变、`board_ops` 无新增；
`GET /ops?since=0` 按 seq 有序无洞、`lastSeq=60`；新连接 join 看到 60；再提交一条后
增量补拉只返回 61。单测（server + web）与 e2e 写路径相关用例（drag / editor / restore / permissions）全绿。

## 5.2 光标合帧后的复测（2026-11-17）

改动（`apps/server/src/realtime/{board,cursorFanout}.ts`、`apps/web/src/collab/{socketClient,BoardCollab}.ts`、
本目录 `realtime-load.mjs`）：

- **服务端每房间合帧**：每个 board 一个 pending Map，`cursor:move` 只覆盖该 `connectionId` 的最新坐标，
  33ms 到点一次性 `emit('presence:cursor:frame', { boardId, cursors, at })`。原来每个 `cursor:move`
  都 `socket.to(room).emit('presence:cursor')`，50 人 × 4Hz = 200 次房间广播/s（每次 49 个接收者），
  现在是 **每房间 30 次/s**，与人数无关。
- **一条消息只编码一次**：帧内所有光标进同一个 payload，socket.io 对一次 emit 只做一次序列化，
  再写到房间内每个 socket；广播次数与序列化次数都从 O(N×Hz) 降到 O(30/s)。
- **客户端批量消费**：`presence:cursor:frame` 到了以后用一次 Map 合并、一次 `emit()` 触发 React 更新
  （原来是每个远端光标一次 state 更新）。`joined.self.connectionId` 下发后客户端按它过滤自己，
  因为合帧统一走房间广播、不再有 `socket.to` 的天然不回显。
- **协议加可选 `t`**：压测客户端在 `cursor:move` 里带发送时刻，服务端原样回带，压测按 `t` 算端到端；
  生产客户端不发这个字段，回归时仍按客户端建连时刻粗略统计。
- **压测脚本支持单类流量归因**：`--cursor-hz 0` / `--op-hz 0` 只关掉对应流量，用于区分「光标扇出」
  与「op 写 + op 广播」各自在某一档里的成本（0 值不再被 `setInterval(Infinity)` 误当成 1ms）。

语义前提（未破坏）：帧内同一连接 **latest-wins**，最后一帧必然携带每个活动连接的最新坐标（停手不再移动
也会在下一帧落地）；同一连接的帧按 TCP 顺序到达，不会倒退到旧位置；断开时 `drop` 掉未发帧，不留幽灵光标；
元素写路径一行没动（仍走 §5.1 的批量提交）。

复测（同一台机器、2s 预热 + 10s 测量、4Hz 光标 + 1Hz op；50/100 各复跑一次看方差）：

| 并发 | 光标 p95 前 → 后 | op ack p95 前 → 后 | 投递率 前 → 后 | CPU 前 → 后 | 判定 前 → 后 |
| ---: | --- | --- | --- | --- | --- |
| 5 | 5 → 49.5ms | 20.32 → 27.95ms | 98% → 98% | 4.9% → 6.4% | PASS → PASS |
| 10 | 5 → 49.4ms | 29.47 → 40.96ms | 97% → 98% | 9.1% → 10.8% | PASS → PASS |
| 20 | 18 → 50.9ms | 38.23 → 49.73ms | 97% → 98% | 15.4% → 15.2% | PASS → PASS |
| 50 | **202 → 93.5ms**（82.8–93.5） | **1021.5 → 190.1ms**（190–195） | 100% → 98% | **68.5% → 28%** | **FAIL → PASS** |
| 100 | **8083 → 266ms**（239–266） | **无 ack → 598ms**（560–598） | **45% → 93%** | **92.4% → 63–65%** | FAIL → FAIL |

读法：

- **拐点从 50 后移到 100**。50 档光标 p95 93ms（阈值 150ms）、ack p95 190–195ms（阈值 200ms）、CPU 28%，
  两次复跑都 PASS；现在是 50 档 ack p95 贴着阈值（余量不足 10ms），光标已有 60ms 余量。
- **低档光标 p95 从 5ms 涨到 ~49ms** 是固定 33ms 窗口的固有代价（33ms 窗口 + 一次刷新），仍远低于
  150ms 阈值；换掉的是「人数一多就指数恶化的广播次数」。（低档的这部分代价已在 §5.4 用自适应帧间隔
  收回到 17–39ms。）
- **100 档从崩溃变成接近可用**：光标 p95 8.1s → 0.24–0.27s、投递率 45% → 93–96%、CPU 92% → 63–65%。
  仍 FAIL，但失败项只剩 join 突发与 ack 延迟，不再是光标秒级 + 大量丢帧。
- 投递率口径说明：这里客户端 4Hz < 帧率 30Hz，一帧基本只含一条该连接的光标，所以「投递/期望」
  仍然接近真实投递；换成 16Hz 客户端时合帧会主动合并中间帧，该比值会低于 1，应以「最新位置是否
  在阈值内到达」为准，而不是帧数。

100 档归因（`--cursor-hz 0` / `--op-hz 0` 各跑一次，其余口径相同）：

| 100 档流量 | 光标 p95 | op ack p95 | 投递/期望 | CPU | 结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| 光标 4Hz + op 1Hz（常态） | 266ms | 598ms | 93% | 63% | 两项都超阈值 |
| 仅光标 4Hz | **61ms** | — | 98% | 21% | 光标路径单独看很宽裕 |
| 仅 op 1Hz | — | **560ms** | 100% | 51% | ack 延迟与光标无关 |

- **光标扇出已经不是瓶颈**：单独压 100 个 4Hz 光标，p95 只有 61ms、CPU 21%；两股流量叠加后才被拖到
  266ms，说明是 op 路径挤占了事件循环与每个 socket 的写队列。
- **这一轮之后的新瓶颈是 `op:apply` 的全房间广播写放大**：100 档 = 100 op/s × 100 个接收者 = 1 万帧/s，
  每帧 ~600B（约 6MB/s 的 ws 写入 + 每接收端一次 JSON 解析），在单进程里把 ack/apply 的 p50 抬到 ~330ms，
  并把光标帧排在后面。单独关掉光标后 ack p95 仍是 560ms，证明它不是光标合帧引入的。
- **另一个独立瓶颈是 join 突发**：100 个 socket 同时握手 + `join`（身份/权限解析、`presence:state` 全量广播）
  p95 0.5–1.4s，改动前后基本一致（1433 → 1258–1444ms），与光标无关（已在 §5.3 处理：100 档 28–30ms）。
- CPU 只到 63%，不是纯算力饱和，而是单事件循环里的序列化 + 每 socket 写入 + 客户端单进程解析共同造成的
  排队延迟；因此下一步的收益点在减少广播接收者（订阅/视口过滤）或减少每帧字节数，而不是加机器核数。

校验：server 92 条单测、web 单测、`npm run typecheck` 全绿；e2e 的 drag / editor / permissions 三组全绿
（含多人同板并发写入、离线回连补拉）。

## 5.3 presence 名单合帧后的复测（2026-11-17）

改动（`apps/server/src/realtime/{board,presenceFanout}.ts`，客户端零改动）：

- 新增 `presenceFanout`：每个房间一个「脏标记 + 100ms 定时器」，join / leave 只 `touch`；到点从注册表
  实时聚合一次**权威全量名单**，单次 room emit。原来每次 join / leave 都在响应路径里
  `ns.to(room).emit('presence:state', 全量名单)`，100 人进房 ≈ 100 次广播 × 100 个接收者 × ~15KB。
- 协议不变：客户端仍收 `presence:state` 全量快照，只是到达时间改为「≤100ms 的下一帧」。
- 注册表仍在 join / leave 时**同步**更新，所以合帧只影响广播节奏，不影响断线清理的最终一致性。
- 新增 3 条单测：同窗口多次变化只发一帧、下个窗口重开、房间已空不广播。

| 并发 | join p95 前 → 后 | 光标 p95 前 → 后 | ack p95 前 → 后 | 投递率 前 → 后 | CPU 前 → 后 | 判定 前 → 后 |
| ---: | --- | --- | --- | --- | --- | --- |
| 5 | 18.2 → 12.3ms | 49.5 → 48.5ms | 28.0 → 19.8ms | 98% → 98% | 6.4% → 4.8% | PASS → PASS |
| 10 | 30.4 → 17.6ms | 49.4 → 48.3ms | 41.0 → 38.3ms | 98% → 98% | 10.8% → 3.7% | PASS → PASS |
| 20 | 63.2 → 11.0ms | 50.9 → 48.9ms | 49.7 → 34.7ms | 98% → 98% | 15.2% → 7.2% | PASS → PASS |

**拐点**：本轮 5/10/20/50/100 全部 PASS，100 档不再是失败档；此前拐点在 50、第二项后后移到 100 边缘，

- 光标 / op 未被拖慢：光标 p95 48–68ms（与第二项后 49–94ms 同量级），ack 与投递率持平或更好；
  元素写路径未改动。

## 5.4 自适应合帧后的复测（2026-11-17）

§5.2 的固定 33ms 合帧把 50/100 档救了回来，但把低档一起拖慢：5/10/20 档光标 p95 从 5ms 变成 48–49ms，
人少的常态场景观感是「慢半拍」。这一轮只改 `apps/server/src/realtime/cursorFanout.ts` 的帧间隔策略，
合帧与广播方式、协议、客户端、写路径都不变。

分档与迟滞（活跃连接数 = 最近 2s 内移动过的 `connectionId` 去重数）：

| 档位 | 帧间隔 | 进入条件（从上一档） | 退出条件（迟滞） | 约合帧率 |
| --- | ---: | --- | --- | ---: |
| fast | 14ms | 新房间默认；或从 mid 回落 | 活跃 > 10 才升 mid | ~70fps |
| mid | 24ms | 活跃 > 10（自 fast）；或活跃 < 30（自 slow） | 活跃 < 7 回 fast；活跃 > 36 升 slow | ~40fps |
| slow | 33ms | 活跃 > 36 | 活跃 < 30 才回 mid | ~30fps |

- **迟滞**：上升与下降用不同阈值，档与档之间留 3–6 个连接的缓冲带（fast↔mid 是 11 升 / 6 降，
  mid↔slow 是 37 升 / 29 降）。人数在阈值附近波动时不会逐帧反复横跳。
- **只在窗口边界切档**：每次 `flush` 用本窗口观察到的活跃数算下一窗口的间隔，窗口中途不变，
  所以一次切档至少稳定一整帧，不会因为单条 `cursor:move` 抖动。
- **活跃口径**：`push` 时记 `connectionId → now`，`flush` 时清掉超过 2s 没动的连接。围观者、
  已停手的人不算进档位，人数下降能自然回落。
- **新房间从 fast 起步**：绝大多数板子人少，第一帧就该跟手；人数多时 1–2 帧内升到对应档位。
- **状态释放**：房间连续 2s 没有新光标后释放整个房间状态（`pending` / `active` / 定时器），
  不会按板泄漏；下次有人动光标重新按 fast 起步。
- **语义不变**：每档都是固定窗口 + 帧内 latest-wins；`push` 必进 pending、定时器必发，停手最后一帧
  仍会落地；同一连接每帧最多一条、按序发出，不会倒退；`drop` 仍然清掉未发帧，不留幽灵光标。

为什么 fast 取 14 而不是 16：Windows 的定时器粒度是 **15.625ms**，`setTimeout(16)` 会被抬到 ~31ms
（两跳），`setTimeout(14)` 才稳定落在一跳（实测 p95 16.6ms；`setTimeout(8)` 也是 ~16ms）。同理 mid 的
24ms 在 Windows 上实际落到 ~31ms、slow 的 33ms 落到 ~47ms。也就是说：Windows 下三档的实际周期约为
**16 / 31 / 47ms**，Linux/macOS 下为 **14 / 24 / 33ms**。这不影响结论，但能解释下面 20 档为什么是 39ms
而不是 24ms。

复测（同一台机器、2s 预热 + 10s 测量、4Hz 光标 + 1Hz op，单进程压测端；前值取 §5.3 固定 33ms 同口径）：

| 并发 | 档位 | 光标 p95 前 → 后 | ack p95 前 → 后 | 投递率 前 → 后 | CPU 前 → 后 | 判定 前 → 后 |
| ---: | --- | --- | --- | --- | --- | --- |
| 5 | fast | 48.51 → **24.0ms** | 19.81 → 20.1ms | 98% → 98% | 4.8% → 3.6% | PASS → PASS |
| 10 | fast | 48.34 → **17.35ms** | 38.25 → 23.53ms | 98% → 98% | 3.7% → 1.9% | PASS → PASS |
| 20 | mid | 48.89 → **39.35ms** | 34.68 → 22.48ms | 98% → 97% | 7.2% → 3.6% | PASS → PASS |
| 50 | slow | 49.48 → 48.47ms | 49.77 → 39.75ms | 98% → 97% | 10.6% → 10.0% | PASS → PASS |
| 100 | slow | 67.6 → 70.81ms | 192.26 → 184.31ms | 98% → 98% | 22.3% → 21.1% | PASS → PASS |

读法：

- **低档回到两位数毫秒**：5/10 档 48ms → 17–24ms，20 档 → 39ms，都在两位数、且阈值余量很大。
- **50/100 不退步**：两档都还落在 slow（33ms 档），p95 48.5 / 70.8ms 与固定 33ms 的 49.5 / 67.6ms
  在复跑方差内（100 档历史范围 58.9–73.8ms），CPU 也没有上升（10.0% / 21.1%）。
- **CPU 全面下降**：低档少了约 1–3.6 个点的合帧/扇出开销，高档持平。
- **拐点未变化**：本轮 5/10/20/50/100 全部 PASS，100 档的约束仍是 §8 待办里的 `op:apply` 广播写放大
  （ack p95 184ms 贴近 200ms 阈值），与帧间隔无关。

中间试过的一版把 fast 设为 16ms，5/10/20 档只有 32.7 / 32.5 / 38.6ms（`results/realtime-20261117-181800`），
正是被上面那条 15.625ms 粒度抬成了两跳；改成 14ms 后才拿到 17–24ms。

语义校验：`cursorFanout.test.ts` 新增 6 条用例，覆盖三档阈值与上下迟滞边界、帧内 latest-wins、
12 活跃时首窗 fast / 下一窗切换到 mid、`drop` 后不产生幽灵帧、房间释放后重新按 fast 起步；
server 16 个测试文件全过、typecheck 通过，e2e 的 drag / editor 两组全过（含多人同板并发写入、
离线回连补拉），客户端与写路径均未改动。

## 6. 本地单机数字 vs 生产（多实例 + redis adapter）

| 因素 | 本地单机 | 生产多实例 | 对容量数字的影响 |
| --- | --- | --- | --- |
| 网络 | loopback，无 TLS / 反代 / 跨机 RTT | 客户端→LB→实例，每跳 1–50ms | 生产同 CPU 下广播 p95 会整体抬高；但 200ms 口径下 20 人仍有大量余量 |
| 运行时 | tsx watch + debug 日志（每个 op 一条 info、join/leave 一条 debug） | 编译产物 + info 日志 | 生产单 op 事务与广播会更快，单实例数字可能高 1.5–2 倍 |
| 光标广播 | 单进程扇出，受单核限制 | 每实例只扇出本地连接，可水平扩 | **光标容量可随实例数近似线性扩**；但每帧仍要过 1 次 Redis `PUBLISH`，单 Redis 是共享上限（当前量级远未到） |
| 元素写入 | 单板 advisory lock 串行，实测约 50 op/s | **完全一样**：锁在 Postgres，所有实例共享 | 加实例不会提高**同一块板**的写吞吐，只会增加等锁者；跨板并发才能靠实例数扩 |
| presence | 全量在本实例内存 | 代码就是按实例存的（文档 §6.3 / §13 明确说明不跨实例聚合） | 多实例下「在线人数/光标列表」天然不完整；容量测试里的 N 也不等于全局在线数 |
| DB 池 | 10 | 实例数 × `DB_POOL_MAX` | 多实例时总连接数要和 `max_connections` 对账；单板写吞吐仍受 advisory lock 限制 |
| 其他 | 开发机后台任务、Windows 网络栈 | 容器 / Linux | Linux 下 socket 写入通常更便宜，单核光标上限会更高 |

因此：本机测出的是「单实例 + 单板 + 无网络延迟」的**乐观上界**；生产真实单实例容量通常更低，
而跨板并发可以靠加实例扩，单板写容量不能。要把单板容量抬上去，需要动写路径本身
（按元素/分片加锁、写队列合并、或改 CRDT/异步落库），以及给光标做节流/兴趣管理。

## 7. 复现注意事项

- 先启动 dev server；脚本不会替你启动，也不会在结束时动它。
- 要拿到干净数字：不要在压测期间修改 `apps/server/src`（tsx 会重启，实测会显著污染 50/100 档）；
  尽量让 dev 日志处于 info 而非 debug（当前 dev 为 debug，这本身会吃掉一部分 CPU）。
- 100 档在未优化时会把 dev server 打到 ~99% 单核；§5.1–§5.3 三项优化后，100 档服务端 CPU 约 22%，
  但压测期间仍不要用它做别的事。
- 结果只保留最近一次的报告；需要多次取样时用 `--out` 分目录（例如 `--out .verify/loadtest-run2`）。

## 8. 后续待办（按优先级）

1. **`op:apply` 全房广播写放大（当前第一瓶颈）**。证据：100 档 = 100 op/s × 100 个接收者 = **1 万帧/s**，
   每帧 ~600B ≈ **6MB/s**；单独压 op（`--cursor-hz 0`，`results/diag-presence-fixed-op-only/`）时
   **ack p95 182ms、CPU 仅 17.6%**，叠加光标后 ack p95 192ms。特性是 **CPU 不高、延迟来自排队**：
   单事件循环里每个 socket 写一帧 + 每个接收端一次 JSON 解析。注：§5.2 记录的「560ms / CPU 51%」
   是 presence 合帧前的同口径测量，混入了 join 风暴的余波；合帧后的干净数字是 182ms / 17.6%。
   方向：按视口 / 订阅过滤接收者、op 广播合帧、压缩每帧字节，而不是加核。
2. **单板写吞吐受 advisory lock 限制**（实测约 50 op/s 量级），加实例不会提高同一块板的写吞吐，
   只会增加等锁者；跨板并发才能靠实例水平扩。
3. **presence 仍是单实例内存**（见 §6 表格），多实例下在线名单不完整；要跨实例需要 Redis 存储或
   改走 adapter 广播，成本与一致性需要单独评估。
4. **200 档未测**：100 档已 PASS，但 ack p95 152–192ms 已贴近 200ms 阈值，真实拐点预计在 100–200
   之间；需要时加一档定位。
